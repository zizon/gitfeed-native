# Review, 2026-11-09

Point-in-time review of the package at `8ccf65c`. Scope: every file under
`src/` (about 6,300 lines), `tests/`, `docs/jobs.md`, `docs/cloud-sync.md`,
`README.md`, `cordis.patch.yml`, `build.mjs`. Gates at the time of review:
`pnpm build` ✓, `pnpm lint` 0 warnings / 0 errors on 43 files, `pnpm test`
10/10 suites.

Two readers went through it: the Client half line by line, the Host half in a
separate pass, with every claim below re-checked against the source before it
was written down. Nothing here is a suggestion to rewrite; the fix for each is
the smallest one that removes the failure.

Verdict: the **shape is good and the discipline is real** — one clock, one
request surface, one published snapshot, a lint rule set that is actually
enforced, and a Host half with no shell interpolation and no `any`. What is
wrong is narrower: **two stores of items and several code paths that only know
about one of them**, one disabled code path in the keyboard arbitration, and a
sticky-row policy that only exists when grouping is on. The docs are accurate
about architecture and stale about behaviour that changed in the last three
commits.

## A. Data-correctness bugs (Host)

### A1. The refresh cache cannot see the committed archive — duplicates, dead repairs *(high)*

`fetch.ts:303-309` builds the dedupe map `known` from `itemsDir` alone. The
runtime fetch writes `dataDir: '.local'` (`service.ts:402-404`), so `known`
never contains the rows committed in `data/items`. Reading is the other way
round: `service.ts:169-172` lists `data/items` shards **first** and
`service.ts:196-200` keeps the first row per id.

Consequences, both present in the checkout today:

- every item a feed re-serves is appended to `.local/items` again — 2,131 of
  the 2,203 ids in `.local/items` also exist in `data/items` — and every one
  of them is counted in the run's `added` and in the toast;
- the repair pass (`fetch.ts:357-369`) writes the longer summary into `.local`,
  where `buildItems` then discards it in favour of the committed row: two
  repairs are invisible right now.

Fix: seed `known` from both shard directories, and on a duplicate id prefer the
longer summary in `buildItems`.

### A2. Unsubscribing leaves the worktree permanently dirty *(high)*

`service.ts:484-489` deletes the feed's rows from `data/items` **and**
`.local/items`. `sync()` stages an explicit list that stops at
`data/read.ndjson`, `data/starred.ndjson`, `feeds.json`, `config.json`
(`git.ts:110`), so the deletion can never be committed. The dirty probe covers
`data` (`git.ts:58`), so after one unsubscribe the status line says
"uncommitted" for good, and the sync job keeps taking its commit branch for a
change it will never stage.

Fix: add `data/items` to the staged list, or stop writing the committed store
from `removeFeed`.

### A3. The fetch timeout stops at the response headers *(medium-high)*

`fetch.ts:103-108` clears the abort timer in a `finally` around `fetch()`;
`fetch.ts:119` then awaits `res.text()` with no deadline. A server that sends
headers and stalls the body holds that slot until undici's own default, and
`concurrency: 6` means six such feeds wedge a run. `feeds.ts:110` gets this
right for discovery (`AbortSignal.timeout` spans the body).

Fix: move `clearTimeout` after `res.text()`.

### A4. `addFeed` and `removeFeed` mutate `feeds.json` outside the write queue *(medium)*

`serialize()` (`service.ts:145-149`) is used only by `setState`. Both feed
mutations are read-modify-write over the same file (`service.ts:435-456`,
`:475-482`), and `writeJson` is not atomic (`store.ts:18-21`). Two overlapping
subscribes — UI plus agent tool is enough — lose one; a fetch reading mid-write
gets `{}` and fails the whole run with `feeds.json is missing or has no
"feeds" array` (`fetch.ts:57-60`).

Fix: wrap both in `serialize()`, and write `feeds.json` through temp+rename.

### A5. Committed `meta.json` wins the title, so a renamed feed never renames *(medium)*

`service.ts:226-235` merges the two meta stores per field and prefers `data/`
for `title`, `folder`, `siteUrl` and `url`; only `lastError` picks the newer
`checkedAt`. Since the plugin fetches into `.local`, an upstream title change
can never reach the sidebar.

Fix: choose the whole entry by `checkedAt`, then fall back per field.

### A6. A disabled feed loses its archived items and its title *(medium)*

`fetch.ts:66` drops `disabled` entries when building the runnable list;
`fetch.ts:290` then derives `live` from that filtered list and
`fetch.ts:315` → `dropOrphans` (`fetch.ts:221-232`) rewrites the shards to
delete every item of the disabled feed, and `fetch.ts:293-299` deletes its
meta. `readFeeds` (`feeds.ts:36-42`) does not filter, so `buildSnapshot` still
lists the feed — with no items and no name. `disabled` is documented in
README's `feeds.json` example.

Fix: keep disabled feeds in `live` and skip them only in the fetch loop.

### A7. Unsubscribe rewrites shards the fetch job may be appending to *(medium)*

`removeFeed` reads, filters and truncate-writes every shard (`service.ts:484-489`)
while a background fetch appends to the same files (`fetch.ts:396`). The runner
serializes jobs against each other (`runner.ts:415`) but not against service
writes, so rows appended between the read and the write are lost.

Fix: route both through `serialize()`.

### A8. No write is atomic *(medium)*

`writeJson` (`store.ts:18-21`) and `writeNdjson` (`store.ts:51-55`) write in
place. `writeNdjson` is what rewrites `read.ndjson` on every unmark
(`service.ts:339`) and `writeJson` holds `feeds.json`, `config.json`,
`meta.json` and `schedule.json`. A crash mid-write leaves a truncated
`feeds.json`, which `readJson` turns into `{}` (`store.ts:10-16`) — an empty
subscription list, and the next fetch throws.

Fix: `<file>.tmp` + `rename`.

### A9. A 304 never clears a previous failure *(medium)*

`fetch.ts:111-116` merges the 304 over the previous meta without clearing
`lastError`, and `fetch.ts:348` writes it back. A feed that fails once and then
answers 304 — likely, since its validators are unchanged — stays red forever
(`service.ts:248` surfaces it).

Fix: `lastError: null` in the 304 merge.

### A10. `checkedIds` truncates at 4,000 without saying so *(low, latent)*

`service.ts:83` slices silently. `markEverything` sends every unread id, so
past 4,000 unread the client clears them all optimistically while the Host
marks the first 4,000 and the rest reappear on the next load. The archive is at
3,237. Fix: report the accepted count, or page the request.

### A11. Marks throw away the item cache *(low, perf)*

`invalidate()` drops `itemsCache` (`service.ts:139-142`) and `mark`/`star` both
call it (`service.ts:353`, `:367`), although neither touches item shards —
which is the whole point of the separate `itemsVersion` documented at
`service.ts:124-130`. The `unchanged` short-circuit hides it on the normal
path, but the next full payload after a mark re-parses 14 shards / 5,445 rows
(~250 ms on this archive).

Fix: only `gitCache` is invalidated by a mark.

### A12. Remaining latent Host issues

- `git status` (`git.ts:58`) can collide with `sync()`'s index writes; on
  collision `readGitInfo` catches and reports `{repo: false}` (`git.ts:70-72`),
  so the rail flickers to "local copy".
- `git add -A` in the first-commit branch (`git.ts:114-115`) would commit
  `.local/` (13 MB of machine-local cache) if a `git init`-ed root never got
  the scaffolded `.gitignore`.
- `textOf` decodes entities **before** stripping tags (`xml.ts:49-53`), so
  `&lt;b&gt;` becomes a tag and is deleted with its text: a title containing
  escaped markup loses it.
- `unwrap` skips entity decoding entirely when the body contains any CDATA
  (`xml.ts:42-46`), so a body with both keeps `&amp;` literal.
- `findTag`/`attr` compile a `RegExp` per call (`xml.ts:61-84`); a run over 374
  feeds is ~200k compilations.
- Two HTML→text pipelines: `plainText` (`service.ts:67-78`, six entities) for
  the tool, `xml.textOf` (a much larger table) for parsing — so the agent
  tool's `query` misses `&mdash;` and numeric refs the reader's search finds.
- `refreshMinutes` defaults to 5 in the plugin (`index.ts:66`) and 0 in
  `createGitfeed` (`service.ts:112`); a direct embedder silently gets no
  refresh.

## B. Client behaviour bugs

### B1. The main-panel page has no keyboard at all *(high)*

`useKeyboard` returns early on a falsy `enabled` in both effects
(`hooks.ts:71`, `:97`). The rail passes `visible` (`GitfeedRail.tsx:130`); the
page passes three arguments (`GitfeedPage.tsx:33`), so `enabled` is
`undefined` and every shortcut is dead on the surface that shows the hint
`j / k move · m read · s star …` (`locales.ts:79`). Only the rail's keys work.

Fix: `if (enabled === false) return`.

### B2. Read rows are never released when grouping is off — which is the default *(high)*

`exhaustedGroups` only reports sections (`derive.ts:154-166`), and the one
caller of `releaseSticky` is the fade effect (`ItemList.tsx:229-240`). With
`groupBy: 'none'` — the shipped default (`settings.ts:16`) — nothing ever
releases, `clearSticky` only runs on filter/query/source changes
(`controller.ts:278-291`), and `listOf` keeps every sticky row listed
(`derive.ts:70`). Scrolling 500 rows in Unread therefore leaves 500 read rows
in the list, and `items.count` counts them, until the surface remounts.

Fix: treat the ungrouped list as one section (release ids scrolled out of the
band), or cap the sticky set by distance from the viewport.

### B3. `escape()` bypasses the sticky reset *(medium)*

`controller.ts:335-341` sets `query: ''` and `feedId: null` through `setUi`,
while the three commands that change the same scope call `clearSticky()`
first (`controller.ts:278`, `:283`, `:289`). Escape therefore keeps sticky rows
across a scope change — the invariant the other three paths maintain.

### B4. `toggleRead` disagrees with both mark policies *(medium)*

`controller.ts:302-308` calls `mark([id], !isRead)` with no `keepList`, so the
row is not sticky, and it bumps the list only when un-marking. Marking read
with `m` therefore leaves a read row in the Unread list with no owner: it stays
until some unrelated event rebuilds the list, and then disappears — the exact
"vanishes at an unrelated moment" the fade commit removed everywhere else.

Fix: pass `keepList` on the read direction and let the section release it.

### B5. Three different maxima for one persisted width *(medium)*

`listW` is clamped to 760 when loaded (`controller.ts:78`), to 900 when written
(`controller.ts:443`), to 760 by the page's splitter (`GitfeedPage.tsx:47`) and
to 900 by the rail's (`GitfeedRail.tsx:142`). Drag to 900 in the rail, reload,
and the pane is 760 again.

### B6. The search index goes stale on a feed rename, and the digest cache is never cleared *(medium)*

`plainCache` is keyed `id:summary.length` (`controller.ts:191`) but its value is
`haystackOf(item, feedTitle)` (`derive.ts:13`), so an upstream title change
leaves search matching the old name forever. `resetText()` clears `plainCache`
only (`controller.ts:133`); `digestCache` (`:88`) is never dropped. And
`plainCache` is a module-level singleton (`:38`) exported for no reason.

### B7. Escape while typing can restore the query it just cleared *(medium)*

`SearchBox` debounces `setQuery` by 120 ms (`Shared.tsx:59-70`) and never
cancels the pending timer when `value` arrives from outside. Type, press
Escape within 120 ms: the controller clears the query, then the timer puts the
typed text back.

### B8. Disposing the transport drops queued marks *(low)*

`dispose()` clears `flushTimer` without flushing (`transport.ts:384-392`), so
any read mark queued inside the 350 ms window is never sent. Flushing once
before teardown is one line.

### B9. Smaller client issues

- `load({force:true})` issued while a plain load is in flight returns the plain
  load's promise (`transport.ts:131`), so the force is silently dropped.
- The stale-model guard compares `payload.itemsVersion !== data().itemsVersion`
  (`transport.ts:175`) — `undefined !== null`, so a Host payload without
  `itemsVersion` would force-reload in a loop. The current Host always sends
  it; the guard should compare against the resolved value.
- `useOutsideClose` re-subscribes on every render because callers pass an
  inline closure (`hooks.ts:58`, `GitfeedPage.tsx:34`).
- The fade effect reads `entries` and `finishedSet` from its closure but
  depends on `finishedKey` (`ItemList.tsx:229-240`); a rebuild inside the
  380 ms window releases the previous entry list's ids.
- `ItemList` calls `controller.getList()` during render (`ItemList.tsx:34`),
  which can recompute and cache — a read with a side effect.
- `FeedRail` mutates its `seen` ref during render (`FeedRail.tsx:179-186`).
- Two independent lifetimes for one toast: 3500/8000 ms in the controller
  (`controller.ts:148-151`) and 4000/7000 ms in the `Toast`
  (`Shared.tsx:238`).
- `showDigest`'s default (`true`) is hard-coded in two components
  (`ItemList.tsx:37`, `Shared.tsx:104`) and is the only reader pref with no
  server-side default.
- `.gf-fade` has no `prefers-reduced-motion` override, while `.gf-row-in` does
  (`styles.ts`, both blocks) — new motion, missing the guard the file already
  established.
- Row heights are a contract in two places: `ROW_H`/`ROW_H_PLAIN`/`GROUP_H`
  (`constants.ts:10-13`) and `.gf-row`/`.rows-plain`/`.gf-group` in the sheet.
  Nothing asserts they agree, and the virtualizer breaks silently if they
  don't.

## D. Code shape

1. **Six copies of "the message of an unknown error."** `client/util.ts:7`,
   `host/http.ts:61`, `cli.ts:55`, `host/git.ts:12` (this one adds stderr),
   `host/runner.ts:184` and `host/service.ts:60` (identical to each other), plus
   an inline variant at `fetch.ts:190`. One helper in `src/shared/` would cover
   both halves; the client already imports its copy from `util.ts`.
2. **Three descriptions of the `/state` payload.** `shared/types.ts:70`
   (`StatePayload`) is referenced nowhere and is stale — no `itemsVersion`, no
   `itemsUnchanged`, `items` required; the service derives its own
   `StateResponse` (`service.ts:24`); the client hand-writes a third
   (`transport.ts:26`). Delete the dead one, or make it the single source both
   halves import.
3. **`service.ts` is four modules: 624 lines.** The item model (`buildItems`),
   the snapshot merge (`buildSnapshot`), the tool queries (`listForTool`,
   `getForTool`, `statusForTool`, ~90 lines that never touch HTTP), and the job
   wiring. `getState` alone is 47 lines with three early-return payload shapes
   that have to stay in sync by hand (`service.ts:273-319`).
4. **`ItemList.tsx` is 519 lines** — derivation, windowing, marking, the mark
   menu, the section header with its unsubscribe confirm, and the pinned bar.
   The three mechanisms it coordinates (anchor, sticky, fade) are all refs and
   timers in one component.
5. **The two biggest client files have no tests.** `window.ts` and `derive.ts`
   are pure and well covered (46 assertions); `controller.ts` (509!) and
   `transport.ts` (412) are covered indirectly at best. Every Client bug in
   section B except B1 lives in those two files, and B2/B4/B5/B6 are all
   cache-key or clamp arithmetic that a 20-line suite would catch.
6. **Module-level mutable singletons**: `plainCache` (`controller.ts:38`) and
   the keyboard arbitration (`hooks.ts:7-9`). Both outlive the controller they
   serve, which is what makes B6 a bug rather than a cache miss.
7. **`primitives.d.ts` (193 lines) and `store.d.ts` (25)** hand-maintain a slice
   of two shared modules' APIs. They are the only thing that can drift from the
   platform silently, and they already needed `children` added once.
8. **Misleading names**: `titleCase` (`opml.ts:26`) decodes and trims, it does
   not title-case; `listForTool().total` (`service.ts:556`) is the number of
   rows returned, not the number of matches.
9. **Dead weight**: `DIGEST_CHARS` (`constants.ts:14`) is unused while
   `digestText` hard-codes `max = 240` (`util.ts:151`); `plainCache` is
   exported and never imported; `FeedOutcome.failed` (`schedule.ts:23`) is
   never read; `EmptyArticle` declares a `state` prop it ignores
   (`Shared.tsx:300`); `lastScopeMark.read` is always `true`
   (`controller.ts:349`), so `!last.read` is decorative; the `keepList`
   parameter is documented as a three-state decision but `false` and `undefined`
   behave identically.
10. **Test affordances in production types**: `JobTimers.timeout` returns
    `void | Promise<void>` (`runner.ts:125`) so a fake clock can await a pass.
11. **Two truthiness policies**: `toBool` (`settings.ts:41-51`) and `envBool`
    (`index.ts:39-46`) parse the same six spellings, with different input
    handling and different fallbacks.
12. **Job option objects use method syntax** (`jobs.ts:30-37`, `:162-171`),
    which invites the `this`-binding mistake the Client already hit once
    (`unbound-method` forced arrow properties in `transport.ts`).
13. **`GitfeedRail.tsx` imports `../util.js` twice** (lines 14 and 18).
14. **One clock, and it is enforced.** `tests/architecture.test.mjs` is the best
    thing in the test suite: it greps the Host half for a raw timer and pins the
    `JobTimers` surface to exactly `timeout`. Keep it.

## E. What is clean

- `settings.ts`, `scaffold.ts`, `http.ts`, `git.ts`, `tool.ts`, `index.ts` —
  no `any`, no shell interpolation (`execFile` with argv arrays), explicit 404
  and 405 paths, a same-origin fence, a 1 MB body cap, and error paths that
  cannot crash a run without reporting it.
- `derive.ts` and `window.ts` — pure, documented, and tested; the only two
  modules where the comment and the code agree on every line.
- `prefs.ts` — one snapshot, one migration, and a suite that proves both the
  seed and the durability (including the two bugs it was written to catch).
- The `ctx.effect` disposal discipline: every timer, listener, style and
  registration in both halves is registered for teardown.
